==================================================

Inspect all places where passwords are:

- stored
- generated
- returned
- displayed
- logged
- reset
- bulk reset

Passwords must remain bcrypt hashed for authentication.

STOP storing reusable plaintext/display passwords.

Do not expose existing passwords to admins, students, teachers or parents.

If the system needs an admin-created temporary password:

- never log it

- remove persistent plaintext password storage now

5. HARDEN JWT AUTHENTICATION
==================================================

Inspect the JWT implementation carefully before modifying it.

The audit found:
- token lifetime may default to one year
- tokens may be accepted through query parameters
- logout is client-side only
- no revocation store was found

Implement the safest low-risk improvements possible.

A. STOP accepting authentication JWTs through URL/query parameters.

Authentication tokens should be accepted through the existing Authorization Bearer mechanism or another established secure transport already used by the application.

Do not put JWTs in URLs.

B. Review JWT expiry.

If the system currently falls back to a one-year expiry when configuration is missing, replace that fallback with a significantly shorter sensible production default.

Prefer an environment-configurable setting such as:

JWT_EXPIRES_IN

Use a conservative default such as 12h or 24h if no value is configured.

Document the chosen value.

Do NOT hard-code a new secret.

JWT signing secret must remain an environment variable.

C. Do not build a complicated token revocation service in this deployment unless necessary.

The Student Portal retirement phase will separately address existing student sessions.

D. Make sure Admin, Staff and Parent login still work after these changes.

6. HARDEN PARENT OTP
==================================================

The audit identified:

- OTP generation using Math.random()
- plaintext OTP storage
- no visible attempt throttle
- possible development fallback exposing OTP

Fix this carefully without breaking Parent password reset.

A. OTP GENERATION

Use Node's crypto module.

Generate OTP values cryptographically securely.

Example concept:
crypto.randomInt(...)

Do NOT use Math.random().

B. OTP STORAGE

Do not store OTP values in plaintext.

Store a hash of the OTP.

When the parent enters an OTP:
- hash/verify securely
- compare against the stored value
- never expose the stored hash

C. OTP EXPIRATION

Ensure OTPs have a short expiration period.

If an existing appropriate expiry exists, preserve it.

If not, use a reasonable short expiry such as approximately 10 minutes.

D. ATTEMPT LIMITING

Introduce reasonable limits against OTP guessing.

For example:
- limit verification attempts per OTP/request
- invalidate after repeated failures
- rate limit OTP requests by phone/account/IP where practical

Do not implement limits so aggressively that normal parents are locked out unnecessarily.

E. GENERIC RESPONSES

Avoid revealing whether a specific parent/mobile number exists where possible.

F. DEVELOPMENT FALLBACK

OTP values must NEVER be returned to the browser/client or included in API responses in production.

Do not log OTP codes in production.

Any development-only testing behaviour must be strictly gated by NODE_ENV !== 'production'.
