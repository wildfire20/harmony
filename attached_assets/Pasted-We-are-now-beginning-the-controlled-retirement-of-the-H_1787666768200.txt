We are now beginning the controlled retirement of the Harmony Learning Institute Student Portal.

Security Hardening Phase 1 has already been successfully deployed and verified in production.

This task must REMOVE LEARNER LOGIN ACCESS while preserving the learner records that Admin, Staff, Parents, attendance, fees, reporting and school management depend on.

IMPORTANT:

DO NOT rebuild the management system.

DO NOT:

* delete student users
* archive active students
* set enrolled learners `is_active = false`
* change `role = 'student'`
* change learner IDs
* create a new learners table
* migrate learner records
* modify parent/student relationships
* remove attendance
* remove grades/results
* remove invoices or fee assignments
* remove historical submissions
* remove documents
* remove class/grade assignments
* alter Parent Portal functionality
* alter Staff Portal functionality
* alter Admin functionality

The learner `users` rows must remain operational school records.

The goal is ONLY:

**Learners remain in the management system, but learners can no longer authenticate into a Student Portal.**

# 2. USE A GLOBAL STUDENT PORTAL FEATURE FLAG

Do NOT add a database column during this phase unless absolutely necessary.

Because Harmony is retiring learner login for all learners, implement a global environment/configuration feature flag:

`STUDENT_PORTAL_ENABLED`

Expected behavior:

`STUDENT_PORTAL_ENABLED=true`
= Student Portal operates normally.

`STUDENT_PORTAL_ENABLED=false`
= learner authentication and learner-facing access are disabled.

Production will eventually use:

`STUDENT_PORTAL_ENABLED=false`

Choose a safe default.

Prefer the default to preserve existing behavior if the environment variable is absent during development, unless there is a strong reason otherwise.

Document the exact behavior.

This flag must control student authentication independently from:

* `users.is_active`
* `users.role`
* learner IDs
* grade/class status

Do not reuse `is_active` to disable learner login.

# 3. DISABLE STUDENT LOGIN

Inspect the existing student authentication endpoint:

`POST /api/auth/login/student`

`STUDENT_PORTAL_ENABLED=false`

Return an appropriate generic response such as:

"Student Portal access is currently unavailable."

Do not reveal account existence, passwords or internal details.

IMPORTANT:

Parent login must continue.

Staff/Admin login must continue.

No other user role should be affected.

# 4. BLOCK EXISTING STUDENT JWT SESSIONS

Disabling NEW login is not enough.

A learner who already has a valid JWT must no longer be able to continue using Student Portal features when:

`STUDENT_PORTAL_ENABLED=false`

Inspect the central authentication middleware.

When an authenticated user has:

`role = 'student'`

and:

`STUDENT_PORTAL_ENABLED=false`

deny student-authenticated access.

Do this centrally where practical so existing student JWTs are effectively invalidated without modifying learner database records.

IMPORTANT:

This check applies to the AUTHENTICATED USER being a student.

It must NOT prevent Admin, Staff or Parent users from accessing records belonging to learners.

For example:

Teacher authenticated user → accesses learner attendance:
ALLOW.

Parent authenticated user → accesses linked child:
ALLOW.

Admin authenticated user → manages student record:
ALLOW.

Student authenticated user → attempts Student Portal/API:
DENY.

Be extremely careful with this distinction.
