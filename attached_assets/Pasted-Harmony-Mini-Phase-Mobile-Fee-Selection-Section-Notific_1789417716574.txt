ISSUE 2 — One-Off Fees do not notify Parents

Admin can currently create a One-Off Fee from:

Admin → Payments → One-Off Fees

Example:

Fee: gold reef
Amount: R1,000
Assigned to: Grade 2
Due date: 17 September 2026

The fee correctly appears inside the affected Parent's Fees page.

However:

Parent receives no notification
no unread indicator appears on Fees
no email is sent

This must be fixed.

3. Target ONLY affected Parents

When a one-off fee is created/assigned, determine which learners actually received the fee.

Notify only Parents linked to those learners.

Example:

One-Off Fee assigned to Grade 2

should notify Parents with linked Grade 2 learners.

Do NOT send the notification to every Parent in the school.

For multi-learner families:

one Parent with two affected children should not receive unnecessary duplicate generic emails
the portal notification may identify the relevant learner where useful
preserve learner isolation/security

Never expose one learner's fee to an unrelated Parent.

4. Create durable Parent notification

Use the existing Parent notification/event infrastructure.

When the one-off fee transaction has successfully committed, create a notification similar to:

New fee available

A new one-off school fee has been added.
Open Fees to view the details.

Deep link:

/parent/fees

If the existing notification architecture supports metadata, safely associate:

notification type
fee ID
learner ID where appropriate
target section = fees

Do not include private financial history in the notification.

6. Badge behaviour

Use the existing persisted notification/read-state system.

The badge must survive:

browser refresh
logout/login
switching devices where supported by the current notification architecture

It must not be a temporary React-only counter.

When the Parent opens the relevant section, mark only the appropriate notification(s) for that section as read according to the existing notification model.

Example:

Calendar unread = 2
Fees unread = 1

Parent opens Fees

Fees unread → 0
Calendar unread remains 2

Do not clear every Parent notification just because one section was opened.

If existing notification semantics require the user to view an item rather than merely opening a page, preserve whichever approach is safest and document it.

9. Email must occur AFTER database commit

The sequence must be:

Create fee
↓
assign learners
↓
create durable Parent notification(s)
↓
COMMIT
↓
send Parent email(s)

A Gmail failure must NOT roll back an otherwise valid fee assignment.

If sending fails:

log a safe server-side error
retain the portal notification
do not expose credentials or Parent details in logs

Prevent duplicate emails if the create request is retried.

Add appropriate idempotency/deduplication using the fee/event ID and Parent relationship.

Do not interpret this request as:

Email Parents every time anything changes in finance.

For this phase, email is specifically required when a new one-off fee is published/assigned.

Existing Parent notifications for approved/reversed payments should retain their current behaviour.
